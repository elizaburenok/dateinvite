# ТЗ: приложение-приглашение в места (1:1)

> Документ для агента разработки. Термины сущностей и полей — на английском (для кода), пояснения — на русском. Раздел 14 — решения, которые надо подтвердить до старта; их агент не додумывает молча.

---

## 1. Цель и суть

Превратить сценарий «скидываю другу пачку ссылок на места» в одно человечное приглашение-конверт.

Хост собирает личную библиотеку мест (из Telegram-постов и Яндекс.Карт), под конкретный повод собирает подборку из **3–5 мест** и отправляет **одному** человеку ссылку на кастомную страницу-конверт. Гость смотрит превью, выбирает одно место, отвечает. Хост получает ответ в Telegram-бота.

## 2. Роли

- **Хост (владелец)** — есть «аккаунт» = Telegram-идентичность. Собирает библиотеку, отправляет конверты, получает ответы.
- **Гость** — без аккаунта и без установки. Открывает публичную ссылку-конверт, выбирает, отвечает.

## 3. Ключевые принципы (не отступать без явного согласования)

- **Снапшот на момент сохранения.** Все данные места (фото, адрес, гео, мета) кешируются при добавлении. Страница-конверт читает снапшот, а не живые ссылки — она не ломается, если пост удалили или ссылка не открывается.
- **Нечёткое — только с подтверждением человека.** Если место распознано из свободного текста, показываем 1–3 кандидата, хост подтверждает. Молчаливая ошибка недопустима.
- **Бот тонкий.** Бот — только захват (форварды/ссылки) и уведомления. Навигация и сборка конверта живут в Mini App.
- **Контракт разделяет дизайн и данные.** Гость-страница получает данные конверта как JSON по токену и рисует как хочет. Бэкенд не знает о вёрстке.
- **Асимметрия авторизации.** Хост авторизуется через Telegram (`initData`). Гость — публичный неугадываемый токен, без авторизации.

## 5. Жизненный цикл конверта

`draft → sent → opened → answered → (expired)`

| Переход | Триггер |
|---|---|
| draft → sent | хост сгенерировал ссылку |
| sent → opened | первый успешный `GET /invite/{token}` |
| opened → answered | `POST /invite/{token}/answer` |
| * → expired | наступил `expires_at` (если включён) |

`opened` — это ответ на вопрос хоста «дошло / посмотрел ли». `answered` уходит хосту в бота уведомлением.

## 6. Компоненты

1. **Telegram-бот** — захват (форварды постов / вставка ссылок) + уведомления. Несёт идентичность хоста.
2. **Mini App** (Telegram Web App) — дом библиотеки, навигация, сборка конверта. Авторизация наследуется из Telegram.
3. **Резолвер** — Яндекс-адаптер, парсер Telegram-поста, LLM для нечёткого текста.
4. **Бэкенд + БД** — места, конверты, статусы, снапшоты. Генерит токен, отдаёт данные, принимает ответы.
5. **API конверта** — контракт между бэкендом и гость-страницей.
6. **Кастомная гость-страница** — фронтенд хоста, читает JSON, рисует конверт, POST-ит выбор. **Дизайн — зона хоста, ТЗ задаёт только контракт и обязательные элементы.**

## 7. Резолвер — поведение по веткам

- **Ссылка Яндекс.Карт** → развернуть короткую ссылку по редиректу → получить организацию (name, address, category, rating, photo, hours, coords) → `resolved`.
- **Telegram-пост со встроенной гео-ссылкой / локацией** → взять её → геокодинг при необходимости → `resolved`.
- **Telegram-пост только текстом** → LLM извлекает кандидата → геокодинг → вернуть **1–3 кандидата** боту → статус `needs_confirmation` до подтверждения хостом.
- **Ничего не распозналось** → `failed`, сообщить хосту.

## 8. API-контракт

### Хост (Mini App, авторизация через Telegram `initData`)
- `GET /places` — список с фильтрами: `district`, `category`, `tag`, `status`, `q` (поиск по name).
- `PATCH /places/{id}` — правка `note`, `tags`; подтверждение кандидата (`enrichment_status → resolved`).
- `DELETE /places/{id}`.
- `POST /envelopes` — тело `{ place_ids: [...], host_note }` → ответ `{ token, url }`.
- `GET /envelopes` — список с текущими статусами и, для answered, выбранным местом.

### Гость (публично, по токену — без авторизации)
`GET /invite/{token}` →
```json
{
  "token": "abc123…",
  "status": "opened",
  "host_note": "Выбирай, куда поедем в субботу ✨",
  "places": [
    {
      "id": "…",
      "name": "Кооператив Чёрный",
      "district": "Патриаршие",
      "category": "Кофейня",
      "photo_url": "https://cdn.…/p1.jpg",
      "note": "тут сырники топ и тихо по утрам",
      "lat": 55.764, "lng": 37.593,
      "maps_url": "https://yandex.ru/maps/org/…",
      "rating": 4.7
    }
  ]
}
```
`POST /invite/{token}/answer` →
```json
{ "chosen_place_id": "…", "message": "давай к 12?" }
```
Ответ на повторный `POST` по уже отвеченному конверту — идемпотентно вернуть текущий ответ, не плодить дубли.

### Захват (внутренний, из бота)
Входящий форвард/ссылка → резолвер → создать Place (`resolved` или `needs_confirmation`).

### Уведомления
На `answered` → бэкенд шлёт боту сообщение хосту: какое место выбрал гость + его реплика.

## 9. Бот — команды и поведение

- Форвард поста **или** вставка ссылки → резолв → сохранение. Для `needs_confirmation` — ответ с 1–3 кандидатами (inline-кнопки), выбор → подтверждение.
- `/library` (или кнопка-меню) → открыть Mini App.
- Пуш при `answered` (обязательно) и, опционально, при `opened` — см. §14.

## 10. Mini App — экраны

1. **Библиотека** — список карточек + фасеты (район, категория, дата), личные теги, поиск, отдельный вид-инбокс «на подтверждение» (`needs_confirmation`).
2. **Карточка места** — снапшот + правка `note` и `tags`.
3. **Сборка конверта** — выбрать 3–5 мест, добавить `host_note`, сгенерировать ссылку, скопировать/шарить.
4. **Мои конверты** — список со статусами (sent / opened / answered) и, для answered, что именно выбрал гость.

## 11. Гость-страница — обязательный минимум

Открывается по токену, делает `GET /invite/{token}`, рендерит:
- подпись хоста (`host_note`);
- карточки мест в иерархии: **фото → название + район → пометка хоста**; вторично — категория, рейтинг, мини-карта, «открыть в Картах»;
- выбор **одного** места + опциональная реплика → `POST answer`;
- экран «ответ отправлен».

Всё оформление — на усмотрение хоста. ТЗ фиксирует только контракт данных (§8) и наличие перечисленных элементов.

## 12. Приёмочные критерии

- Форвард Telegram-поста с гео сохраняет место со снапшотом и статусом `resolved`.
- Пост без гео (только текст) даёт 1–3 кандидата и не сохраняется как `resolved` без подтверждения.
- Удаление исходного поста/недоступность ссылки **не** ломает ни карточку, ни конверт (снапшот).
- Библиотека фильтруется по району, категории, тегу; ищется по названию.
- Конверт с 3–5 местами генерирует рабочую публичную ссылку без авторизации гостя.
- Открытие ссылки переводит конверт в `opened`; выбор — в `answered`; хосту приходит уведомление в бота.
- Гость-страница полностью строится из ответа `GET /invite/{token}` без доступа к бэкенд-логике.
- Попытка собрать конверт из <3 или >5 мест отклоняется на уровне API.

## 13. Рекомендуемый стек (сменяемый)

- **Бэкенд:** Node/TypeScript или Python; БД — SQLite на старте, Postgres при росте.
- **Бот + Mini App:** Telegram Bot API + Telegram Web App SDK; обязательна серверная валидация `initData`.
- **Резолвер:** Яндекс Places/Geosuggest API (⚠ проверить актуальные условия и лимиты — отдельная задача агента, не закладываться вслепую), LLM для разбора текста.
- **Гость-страница:** статический SPA на любом фреймворке, деплой на статик-хостинг.
- **Токен:** `nanoid` / crypto-random, ≥128 бит, неугадываемый.

## 14. Решения, которые надо подтвердить до старта

1. **Стек** — если у хоста есть предпочтение, оно приоритетнее §13.
2. **Expiry конверта** — включаем ли `expires_at`? Поле уже заложено nullable; в MVP UI можно не показывать.
3. **Статус `opened` хосту** — показывать ли «посмотрел»? Требует пинга открытия страницы (он и так есть в контракте).
4. **Хранение фото** — кешировать у себя или держать ссылки. Рекомендация: кешировать, по принципу снапшота.

## 15. Вне MVP (осознанно позже)

- Групповое голосование (сейчас строго 1:1).
- События/попапы без фиксированной локации (сейчас только физическая точка).
- Публичный запуск и вопрос прав на чужие фото/данные при масштабе (для личного использования сейчас ок).
- Шаблоны конвертов, аналитика, несколько хостов.
